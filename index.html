Fase 0

Preparar la War Room

PMI + Google SRE

Contexto empresarial

NovaMarket opera un comercio electrónico 24×7. Tiene portal web, dos máquinas virtuales, balanceador, base de datos, almacenamiento, Microsoft Entra ID y Azure Monitor. Hoy inicia la campaña CyberNova, con una demanda muy superior a la habitual.

Antes de conocer el incidente, el equipo debe organizarse. Cada persona selecciona un rol y acuerda cómo trabajará.

Guía docente / solución esperada:

No existe una única distribución correcta. Debe haber responsabilidades diferenciadas, canal de coordinación, registro de decisiones y un criterio claro para escalar cambios. La lectura de PMI respalda orientar al equipo, definir estructura, objetivos y normas; la lectura de Google muestra la utilidad de roles claros durante incidentes.

Fase 1

La primera alerta

Detectar

18:05 — Azure Monitor

El tiempo de respuesta del portal pasó de 600 ms a 4,8 s. La CPU de las dos VM supera el 92 %. Los clientes comienzan a reportar lentitud al finalizar sus compras.

Regla de la fase: todavía no propongan solución. Primero separen síntomas de causas.
Guía docente: síntomas confirmados: alta latencia, alta CPU y experiencia degradada. Aún no hay evidencia suficiente para afirmar si el problema está en capacidad, aplicación, base de datos, red o combinación de factores.
Fase 2

La demanda se dispara

Hipótesis

18:12 — Nueva evidencia

El número de usuarios conectados es aproximadamente 4 veces superior al promedio. El sistema intenta crear automáticamente una tercera VM.

Guía docente: una hipótesis razonable es saturación por aumento de tráfico, pero todavía deben considerar comportamiento de la aplicación, consultas a datos, red y disponibilidad de capacidad para escalar.
Fase 3

Falla el escalamiento

Microsoft Learn

18:14 — Error de Azure

La creación de la nueva VM falla con: ZonalAllocationFailed. Azure no logra asignar capacidad suficiente para el tamaño solicitado en la zona seleccionada.

Solución orientadora: Microsoft Learn indica que ante fallas de asignación pueden evaluarse reintentos, otros tamaños, otras zonas/regiones y, para necesidades previsibles de capacidad, reservas de capacidad. La decisión concreta depende de arquitectura, costo, latencia y criticidad. No existe una opción universalmente correcta.
Fase 4

¿Problema técnico o incidente?

Google SRE

18:20 — Impacto de negocio

El 22 % de las transacciones está fallando. Comercial informa pérdida de ventas y servicio al cliente recibe múltiples reclamos.

Solución recomendada: declarar el incidente. En la lectura de Google, cuando el impacto, alcance y complejidad justifican coordinación formal, se activan roles y comunicación estructurada. Aquí ya existe afectación directa a transacciones y ventas.
Fase 5

Tomar decisiones bajo presión

Criterio de ingeniería

18:25 — Mensaje del gerente comercial

“Necesito que solucionen esto ya. Aumenten todos los servidores al tamaño más grande disponible.”

Guía docente: no se debe ejecutar un cambio grande solo por presión. El error de capacidad ya muestra que “más grande” no garantiza disponibilidad; además hay que revisar costo, riesgo, reversibilidad y evidencia técnica. La respuesta correcta es argumentada, no obediencia automática.
Fase 6

Aparece una segunda pista

Causa vs correlación

18:31 — Revisión de logs

A las 17:55 se desplegó una nueva versión del módulo de recomendaciones. Desde ese momento también aumentaron las consultas a la base de datos.

Pregunta clave: ¿que dos eventos ocurran al mismo tiempo demuestra causalidad?
Guía docente: no. Existe correlación temporal, pero aún se debe validar. La campaña elevó tráfico y el despliegue elevó consultas; ambos pueden contribuir. La hipótesis debe probarse con logs, métricas comparativas y, si es viable, rollback controlado.

Fase 8

Comunicación y recuperación

Google SRE

18:44 — Resultado de la mitigación

Se ejecuta rollback. La CPU baja a 67 %, la latencia a 950 ms y los errores de transacción pasan de 22 % a 1,2 %.

Solución recomendada: no cerrar inmediatamente. Validar estabilidad, transacciones, consistencia de datos, logs, métricas y experiencia del usuario. La mitigación muestra mejora, pero el cierre exige comprobar recuperación sostenida.
Fase 9

Postmortem sin culpa

Aprender
Evitar: “el desarrollador cometió un error”. Preferir: describir la condición del sistema o proceso que permitió el incidente.
Solución orientadora del caso:

Causa inmediata probable: la nueva versión incrementó las consultas a la base de datos y elevó el consumo bajo una demanda extraordinaria.

Factores contribuyentes: campaña con 4× de tráfico; intento de escalamiento que falló por capacidad zonal; despliegue cerca de una ventana crítica; falta de rollout progresivo o validación previa suficiente.

Lectura SRE: el postmortem debe buscar mejoras de sistema, herramientas y proceso, no culpables.
